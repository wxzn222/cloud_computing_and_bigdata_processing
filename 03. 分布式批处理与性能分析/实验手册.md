## 1. 为什么不能只看 Worker 数量

在“模拟服务使用分析与规则查询平台”中，实验 02 已经可以在本人笔记本上用 DuckDB 计算合成服务记录的请求与 Token 总量。数据规模增大后，我们可能把工作拆给多个执行进程。问题是：拆分本身也有成本，某些分组会把大量记录集中到一处，多个进程未必比一个查询引擎快。本章通过真实多进程执行，理解计算正确性与并行性能之间的关系。

**批处理** 对一份有边界的数据集执行计算，例如对已经收齐的一天日志统计总量。本章输入仍是固定的 20,000 条合法事件，不是不断增长的实时队列。

**Worker** 是执行任务的工作进程；**Scheduler** 是调度任务与依赖的组件。**Dask** 是支持分块计算与任务调度的 Python 工具，本章用它的 `LocalCluster` 启动多个独立 Worker 进程，使用进程 ID 证明执行边界。它是真实多进程计算，但所有进程仍在同一台 Windows 电脑上，不能据此宣称完成跨主机网络容错或云弹性伸缩。

**分区 partition** 是数据被拆成的块。分区数决定可拆出的工作单元，Worker 数决定可同时执行任务的资源数量；两者不是同一个参数。

```text
同一份 Silver Parquet
  ├─ DuckDB 单机 SQL → 正确性参照
  └─ Dask 数据分区 → 按 service 交换记录 → 分组聚合
                                     ↓
                         核对结果 + 查看分区倾斜 + 分析耗时
```

## 5. 核心源码逐段解释

打开 `coursekit/pipeline.py`，找到 `lab03()`。下面是其中 `LocalCluster` 调用的源码节选，后续计算仍在该 `with` 块内；请在原函数上下文阅读，不要把这段当成独立、可直接运行的示例。

```python
with LocalCluster(
    n_workers=workers,
    threads_per_worker=1,
    processes=True,
    memory_limit='1GiB',
    host='127.0.0.1',
    dashboard_address=None,
) as cluster:
    ...  # 后续计算见原函数
```

`n_workers` 是 Worker 进程数量；`threads_per_worker=1` 控制每个进程的执行线程数；`processes=True` 要求不同进程，而不是把所有任务放在一个线程池中。`memory_limit` 是每个 Worker 的教学限制，不是整台电脑的总可用内存。调度器、驱动进程、SQL 查询和系统本身也会占内存。

`host='127.0.0.1'` 把监听限制在本机。`dashboard_address=None` 关闭可视化面板，减少端口占用与额外界面操作；观察证据保存在 JSON 中。

```python
df = dd.read_parquet(str(silver)).repartition(npartitions=partitions)
```

读取 Parquet 后重设分区数。这里的 Dask 分区是计算组织，和实验 02 的 Parquet 行组不是同一个概念；重分区也不等于把原 Parquet 文件永久改成多个文件。

```python
shuffled = df.shuffle(on='service', shuffle_method='tasks')
```

**Shuffle** 将记录按键重新分配，使相同服务键的数据进入同一哈希分区。这需要序列化、数据交换、调度和临时内存。本机进程之间也有交换成本，不是只要没有跨机网络就免费。

```python
group = shuffled.groupby('service').agg({
    'event_id': 'count',
    'input_tokens': 'sum',
    'output_tokens': 'sum',
    'latency_ms': 'sum',
})
actual = group.compute()
```

前面的操作构造**任务图 task graph**，即有哪些计算以及它们相互依赖的关系；`.compute()` 请求调度器真正执行并将最终小结果取回驱动进程。不是每写一行 DataFrame 表达式就立即完成整个计算。

最后将 Dask 列名与 DuckDB 参照对齐，按 `service` 排序后比较列表。排序是为避免同样结果仅因行顺序不同而被误判。这里比较整数聚合可用精确相等；浮点数聚合通常需要合理容差，而不能无条件要求二进制完全相同。

## 6. 观察倾斜：八分区为什么不均匀

**数据倾斜** 指不同分区的工作量明显不均衡，使一部分 Worker 很忙、另一部分等待。本课程生成器大约按 7:2:1 分配 assistant/search/batch，且只有三个服务键。

显式按 `service` Shuffle 后，最多只有三个承载不同键的非空分区；若不同键哈希碰撞，非空分区可能更少。继续增加分区不会把单个热键自动分成很多份。必须看真实 `partition_rows_after_shuffle`，而不是将 20,000 除以 8 作为实际观测。

```powershell
.\.venv\Scripts\python.exe -m coursekit capture --lab 03 --stage probe-02 -- .\.venv\Scripts\python.exe -c "from coursekit.common import read_json; r=read_json('outputs/lab03/benchmark-w2-p8.json'); n=r['partition_rows_after_shuffle']; print('partition_rows=',n); print('sum=',sum(n),'nonempty=',sum(x>0 for x in n),'max=',max(n))"
```

回答：本章聚合输出只有三个服务，为什么中间任务图仍可能包含很多任务？输出行数、输入行数和任务数分别描述什么？

对于纯 `SUM`/`COUNT`，引擎通常可以先做局部聚合再合并，从而减少交换量。本次显式 Shuffle 便于同学们观察交换与倾斜；生产环境还要根据算子、数据分布和执行引擎选择策略。

### 7.1 四个计时字段的口径

- `duckdb_seconds`：创建查询连接并完成 SQL 参照计算的时间。
- `startup_seconds`：启动 Dask 集群、连接客户端等启动过程。
- `compute_seconds`：主要 Dask 聚合 `.compute()` 的时间，不含集群启动。
- `total_seconds`：从启动集群到完成计算、额外分区诊断与退出的总时间。

程序在主聚合后另外执行 `map_partitions(len).compute()` 来获取分区行数，因此 `total_seconds` 不等于只有一次主查询的完整耗时，也不能简单看作 `startup_seconds + compute_seconds`。比较时写清这一点。

**没有 2 倍加速，是不是失败？** 不是。先检查结果正确、配置相同，再从数据规模、交换、启动与倾斜解释性能。

**分区 8 是不是 8 台机器？** 不是。它是数据块数量；本机 Worker 进程数由 `workers` 决定。

**Worker PID 每次不同正常吗？** 正常。每次启动新的进程，PID 由操作系统分配，不应把示例 PID 当成固定参考值。

**能否只提交 `matches_duckdb=true`？** 不够。还要提供配置、真实 PID、数据哈希、聚合输出、计时口径与个人改动。

**本机多进程能证明生产集群容错吗？** 不能。本实验验证任务在多个进程上的执行与结果一致；跨机器失联、节点替换和共享存储故障需要另设实验环境。
