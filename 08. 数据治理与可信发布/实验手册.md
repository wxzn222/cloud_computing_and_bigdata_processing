## 4. 阶段二：理解检查是怎样产生结论的

### 4.1 检查包装函数

```python
try:
    detail = operation()
    checks.append({"name": name, "passed": True, "evidence": detail})
except Exception as exc:
    checks.append({"name": name, "passed": False, "error": str(exc)})
```

`passed=True` 只发生在实际 operation 正常完成之后。每个 operation 中有真实读文件、查询或断言。异常被收集，便于一次查看多项问题；末尾的 `all()` 决定整体能否发布。

```python
passed = all(row["passed"] for row in checks)
if not passed:
    raise RuntimeError("发布检查失败")
```

这种方式先收集各项证据，再汇总失败状态，便于同学们同时定位多个问题。本课断言按普通 Python 运行，不要使用会关闭 assert 的优化启动选项。

### 4.2 哈希证明什么

`validate_index()` 检查实际文件的 SHA256 是否等于 manifest。它能发现意外修改和陈旧产物，但哈希不是数字签名。如果攻击者同时控制数据与 manifest，单纯哈希不能证明发布者身份。

因此，SHA256 在这里用于检查字节完整性与版本一致性；它不验证内容来源或发布者身份。来源授权、审核、签名与访问权限需要其他机制。

### 4.3 当前索引为什么继承统计版本

规则查询与统计工具共享同一发布单元。索引版本包含实验 04 统计快照哈希，发布说明据此标明虚构规则与合成服务统计对应的快照。仅统计变化也可能要求重建索引；分析大型系统时，可以讨论拆分版本与发布单元的方法，以及拆分后需要维持的一致性。

## 5. 阶段三：权限与隔离检查

公开检索使用 k=20，覆盖所有允许资料，检查每一项的 visibility。内部检索同时作为正例，确认虚构维护规则确实存在且能被内部角色找到。

```python
assert all(h["visibility"] == "public" for h in public)
assert any(h["doc_id"] == "maintenance" for h in internal)
```

仅验证“公开请求没返回蓝鹭”是不够的：如果检索器坏到所有请求都为空，也能通过这种检查。加入内部正例后才能区分“边界有效”与“系统完全不可用”。

隔离检查确认 untrusted 和 retired 不进入索引，并发送固定攻击问题。它证明本课程这条攻击被拒绝、已知不可信资料被隔离。它不证明所有自然语言变体、编码方式或真实模型都不会受到提示注入。

默认服务只做摘录，没有文件删除、发送邮件或任意工具执行接口。因此“资料中的指令没有被执行”的能力边界应从实际可执行动作来说明，而不是用一句提示词承诺。

## 6. 阶段四：真实版本变更与索引篡改

`version_check()` 使用 `TemporaryDirectory` 创建自己的临时目录，复制虚构规则，再加入 quota v3：“模拟服务的用户每周CPU推理配额已经调整为180分钟”。所有改动都在临时副本中完成，不改变主工作区的120分钟规则。

顺序如下：

1. 对复制的语料建立旧索引，保存旧版本；
2. 添加v3，使源文件SHA256变化；
3. 验证旧索引必须抛出 StaleIndexError；
4. 重建后确认 quota 只剩v3；
5. 比较旧版、新版、不同role的缓存键；
6. 向索引文件末尾添加空格，再次验证哈希不一致。

## 7. 阶段五：真实数据库副本中的重放和回滚

门禁按 latest.json 找到实验 04 数据库，以只读方式打开原库，重新聚合每个 service 的请求与 token 总量，逐行与增量汇总比较。若两边不一致，即使文件都存在也不能通过。

随后 SQLite 的 `backup()` 把实际数据库复制到内存。重复插入一条已存在事件：

```python
probe.execute("INSERT OR IGNORE INTO events VALUES (...)", sample)
probe.commit()
assert count_after == count_before
```

此处省略号仅用于展示逻辑，实际源码根据字段数生成占位符，不可将这段当完整SQL复制运行。event_id 主键阻止相同事件重复入库，行数保持不变。

再开启事务，将一条事件 input_tokens 增加999，但不提交，而是 rollback。回滚后重新读取整行，要求与原样本完全相等。

```python
probe.execute("BEGIN")
probe.execute("UPDATE events SET input_tokens=input_tokens+999 WHERE event_id=?", (event_id,))
probe.rollback()
assert recovered == sample
```

这段操作在实际数据的内存副本上复核重放与事务回滚。完整的消费进度与故障恢复链路证据仍来自实验 04；跨机器分布式 exactly-once 还需要协调存储、消息确认和故障模型，本次单机 SQLite 检查没有覆盖这些机制。

默认 20000 个初始合法事件加实验 04 的一条故障恢复新增事件和一条晚到事件后，当前数据库通常为 20002 行。若使用不同规模，应读取 `latest.json` 指向的数据库和对应运行记录，按实际输入解释行数。

## 8. 阶段六：评价与HTTP证据为什么也要检查版本

评价检查应核对冻结记录与当前实现、测试报告的 index_version 与当前索引，以及 questions.jsonl 的 SHA256、测试题 qid 集合和逐题数。只有总分没有逐题证据，不足以验收。

课程摘录服务门槛包含 Recall@3 ≥ 0.75、固定测试负例全部拒答，以及可回答正例的有效接受；全部拒答不能作为可发布结果。冻结记录必须对应当前代码、配置、题集与索引。该门槛描述本合成题集上的结果；真实场景还需要更大且具有代表性的数据、持续测试和人工复核。

`service_check()` 检查请求数至少 20、逐条响应状态 200、无错误且 health 记录中的索引版本与当前一致。它核验实验 07 已保存的请求记录；索引变化后，需要重新启动服务并再次运行真实请求。

| 发布判定 | 八项基线和本人加入第九项检查后的真实结果，失败项及原因 |
| 已知限制 | 合成小题集、单机SQLite、单进程缓存、无真实认证 |
| 恢复步骤 | 哪一层变化后重跑哪些命令，以及保留哪些历史证据 |

恢复原则是根据依赖关系处理，不是遇到任何错误就删除data重来。例如文档变化：重建索引 → 重跑评价 → 重测HTTP → 重跑门禁；服务仅重启：缓存丢失，数据版本不变，重新测量并说明冷/热状态。

撤回虚构规则时，要保证最新撤回状态不会复活旧版。真实系统删除个人数据还需要处理原始资料、索引、副本和缓存；本课程用虚构数据讨论这一流程，不处理真实个人敏感资料。

## 12. 常见问题

| 现象 | 排查 |
|---|---|
| 第一次lab08全失败 | 先检查工作目录和前序产物，不要把文件存在当完成 |
| evaluation refers to old index | 评价对应了旧索引或不同模式，明确冻结设置后重评 |
| Question set changed | 题集已被修改，说明变更，不手改评价哈希 |
| HTTP evidence uses old index | 启动当前服务并重新运行20次真实请求 |
| 固定负例拒答率不足 | 找具体qid，检查权限与门控；不能删除负例 |
| SQLite和汇总不一致 | 检查 latest 指向哪个 run、增量汇总是否来自同次实验 04 |
| 新增检查失败 | 先用真实哈希定位数据层，保留失败evidence |
| 临时故障没有失败 | 检查是否真的改变了副本，以及是否误把manifest同步更新 |
| release_ready=true但LLM引用差 | 本门禁只覆盖默认摘录服务，LLM失败必须在发布说明单列 |
| 8项变为9项后与参考不同 | 个人新增质量检查正常，解释新增检查内容与结果 |

## 13. 自愿 AI 助手、分析题与提交

AI 助手为自愿选项，使用与否不影响评分。同学们可以用它解释异常、检查恢复说明、查询哈希与 SQLite API；依赖图、失效传播预测、新增检查逻辑、隔离状态对照和发布判定仍需本人完成。提交的日志、评价以及本机服务和可选模型的状态必须来自实际操作并如实记录。

5. 本人新增的质量血缘检查捕获了原八项中的什么空缺？
