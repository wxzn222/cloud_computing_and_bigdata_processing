## 1. 数据不断到来时，正确性问题变了

前三个实验对一份固定数据处理一次。本章在“模拟服务使用分析与规则查询平台”中，用合成服务记录模拟事件持续到达、重复投递、写入中断和晚到日志，观察它们如何影响已保存的状态和统计。此时“最后总和正确”必须建立在明确的处理与恢复规则上。

**增量处理** 每次只处理新到的一部分数据，而不是总从头加载全部历史。**微批 micro-batch** 将连续到来的记录按小批次处理，本课程使用每批 500 条。它帮助学习状态与提交边界，但本章输入仍来自已有 Parquet 列表，不是生产消息队列。

**偏移量 offset** 表示消费者已经处理到输入的什么位置；本章使用逻辑记录位置，不是 Kafka 的 topic-partition offset。**检查点 checkpoint** 将已提交位置保存下来，帮助失败后从可靠状态继续。

**事务 transaction** 将一组数据库操作作为一个整体提交或回滚。课程要保证“事件写入”和“对应检查点推进”属于同一个 SQLite 事务，不能只写进一半。

```text
合法事件按 500 条切片
  → 事务开始
  → 校验并按 event_id 写入
  → 推进检查点
  → 一起提交
       └─ 提交前出错：两者都回滚，再重放这一批
```

本章验证的是**单个 SQLite 数据库内，结合事件 ID 去重的事务性效果**：事件写入和检查点推进在同一事务中提交或回滚。日志重放时，同一事件可能再次被读取；依靠去重后，重复读取不必导致重复业务效果。

### 1.1 学习目标

1. 用小状态表解释事务、检查点、幂等和重放之间的关系。
2. 注入提交前异常，核对数据与进度同时回滚并能从磁盘恢复。
3. 在两个事务练习中任选一个完成关键局部改动，再用失败变式验证。

观察晚到事件如何改变历史统计，并解释事件时间与处理时间的区别。本章核对单个 SQLite 数据库内的事务提交、事件 ID 去重和故障后重放结果。

## 4. 表结构与幂等写入

在 `coursekit/pipeline.py` 阅读 `EVENT_FIELDS`、`apply_batch()` 和 `lab04()`。

```sql
CREATE TABLE events(
  event_id TEXT PRIMARY KEY,
  event_time TEXT NOT NULL,
  service TEXT NOT NULL,
  model TEXT NOT NULL,
  input_tokens INTEGER NOT NULL,
  output_tokens INTEGER NOT NULL,
  latency_ms INTEGER NOT NULL,
  status TEXT NOT NULL
);
```

主键让同一个 `event_id` 不能成为两条不同记录。`NOT NULL` 约束要求值存在，但不验证 Token 非负、枚举合法或时间格式，这些规则仍由实验 02 的 `validate_event()` 执行。不要假定数据库列写成 INTEGER 就自动具有所有业务含义。

```python
old = con.execute(
    'SELECT * FROM events WHERE event_id=?', (row['event_id'],)
).fetchone()
if old and old != values:
    raise ValueError('Conflicting duplicate event_id; correction policy is required.')
con.execute('INSERT OR IGNORE INTO events VALUES (?,?,?,?,?,?,?,?)', values)
```

先查已存在内容，是为了防止 `OR IGNORE` 默默吞掉同 ID 不同内容的冲突。完全重复会被忽略，内容冲突则中止事务。问号是**参数化查询**占位符，参数作为数据传入，不用字符串拼接构造 SQL。

## 5. 一次提交必须包括什么

```python
con.execute('BEGIN IMMEDIATE')
```

`BEGIN IMMEDIATE` 开始事务并尝试获取写事务所需的锁。SQLite 支持本地数据库事务，但不是通过这一行获得任意多写者的无限并发；并发写入仍需要锁与冲突处理。

事件处理完后，仍在同一个事务中推进检查点：

```sql
INSERT INTO checkpoint VALUES (1, ?)
ON CONFLICT(id) DO UPDATE
SET offset = MAX(offset, excluded.offset);
```

检查点表只有 ID=1 这一项。`excluded.offset` 是本次准备写入的新值；`MAX` 防止旧批次重放让进度倒退。检查点取最大值只适合本章按顺序处理的单条输入序列；如果多个分区并发并存在“前面的批次未完成、后面的批次完成”，不能盲目取全局最大位置，否则可能跳过空洞。

```python
if fail_before_commit:
    raise RuntimeError('INJECTED_FAILURE_BEFORE_COMMIT')
con.commit()
```

异常刻意发生在 `commit()` 之前。异常分支执行 `rollback()`，所以数据与检查点都不生效。本章注入的是受控 Python 异常并显式回滚，没有物理断电或强制终止操作系统进程；报告须准确说明故障类型。

### 5.1 关闭连接再恢复有什么意义

程序在失败后关闭 SQLite 连接，再用磁盘路径重新连接，重放未提交的新事件。这样可以检查磁盘中的真实状态，而不是只看仍在内存里的 Python 列表。它仍不等于完整服务进程崩溃、消息代理重平衡或跨机恢复，这些需要额外故障注入。

**至少一次投递 at-least-once** 允许相同事件被再次送达；**至多一次 at-most-once** 可能在故障时丢失但不重放；**恰好一次效果 exactly-once effect** 必须明确在哪个范围内承诺没有重复效果。本章只讨论单 SQLite 数据库内的事务与去重结果，不能把术语脱离范围使用。

## 7. 晚到事件与历史结果

**事件时间 event time** 是事件真正发生的时间；**处理时间 processing time** 是处理系统收到或计算它的时间。两者可能不同，网络缓冲或日志回传会导致旧事件晚到。

本章新建的 `increment-late` 发生于 `2026-02-28T23:59:00+00:00`，早于原始事件，但在本次处理的最后到达。它具有新的事件 ID，不能仅因时间旧就当作重复。

当前政策是接受合法晚到事件，随后从数据库重新计算服务汇总。这个 Gold 是全历史按服务汇总，不是时间窗口状态；每次重算都会纳入数据库中已接受的全部合法事件。

**水位线 watermark** 是事件时间进度的估计，用来帮助判断某个窗口是否可以结束或如何处理迟到数据。它不是简单的系统当前时间，也不是看见一个更晚时间戳就保证以前的事件永不再到。

预测：如果 Gold 改为按日聚合，这个晚到事件应更新哪一天？若应用已经把那一天的结果缓存起来，还需要更新哪些版本或缓存键？这些问题将与实验 07、08 的服务与数据版本衔接。

### 8.1 练习 A：提前提交为什么危险

本章 `附件/student_atomicity.py` 是一个**故意含有提前提交错误**的独立小实验。它使用临时数据库，不会修改主实验数据。初次运行能够结束，但应输出 `atomic_contract_passed=false`；这是需要同学们修复的真实失败证据。

```powershell
New-Item -ItemType Directory -Force .\submissions\lab04 | Out-Null
Copy-Item -LiteralPath '.\04. 增量事件处理与故障恢复\附件\student_atomicity.py' -Destination .\submissions\lab04\student_atomicity.py
.\.venv\Scripts\python.exe .\submissions\lab04\student_atomicity.py
```

先看 `COMMIT_EARLY=True` 控制的那行：事件写入后就提交，随后才准备更新检查点。注入异常时，`rollback()` 无法撤销已经提交的事件，所以出现“行已存在、进度仍为 0”。

将 `COMMIT_EARLY` 改为 `False`，让最终 `commit()` 统一提交事件与检查点。修改之前，先在报告写出修复后故障行数与进度的预期。

```powershell

if ($LASTEXITCODE -ne 0) { throw '原子性练习运行失败；先修复代码，再比较差异' }
git diff --no-index -- '.\04. 增量事件处理与故障恢复\附件\student_atomicity.py' '.\submissions\lab04\student_atomicity.py'
```

代码块先检查 Python 是否运行成功，再比较源码差异；Git 返回 1 只表示存在差异。修复后 `rows_after_failure=0`、`offset_after_failure=0`、`atomic_contract_passed=true`；随后恢复处理，最后应有 1 条事件、检查点为 1；重复重放仍只有 1 条事件。输出分别保存到 `student-atomicity-early.json` 和 `student-atomicity-atomic.json`。

**为什么重新运行不会接着上次增量跑？** 主入口一次完整演示所有阶段，每次独立运行以保留对照证据；同一次运行内部才展示关闭连接、重开和恢复。

**检查点是已处理事件数量吗？** 本章恰好用顺序记录位置，并在末尾新增两个事件；一般系统的 offset 不等于唯一事件数，重复、过滤、分区和空洞都可能使它们不同。

**`INSERT OR IGNORE` 能否包办质量校验？** 不能。它只能根据数据库约束忽略冲突；代码仍需检查类型、时间和同 ID 内容冲突。

**恢复后只新增 1 条为何还要重放？** 失败的事务没有提交，需要再次执行；事件 ID 去重让已成功提交的重复记录不产生额外行。
