## 1. 实验内容与目的

前六次实验的程序由命令行调用。本次在本人笔记本上运行“模拟服务使用分析与规则查询平台”的 HTTP 服务，由同机客户端发送请求，观察服务的部署状态与请求指标。知识问答读取实验 05 的虚构规则索引；统计工具直接读取实验 04 的增量汇总；选择模型路径时，可用实验 06 的 token 计量解释推理资源。报告应分别标明这三类数据的来源和单位。

## 2. 先认识服务的四个对象

| 对象 | 本实验例子 | 它不是什么 |
|---|---|---|
| 进程 | Uvicorn 运行 `coursekit.service:app` | 不是 Python 文件存在就代表服务启动 |
| 地址和端口 | 127.0.0.1:8000 | 不是模型文件地址 |
| 路由 | `/health`、`/ask`、`/stats`、`/metrics` | 不是磁盘上的同名文件 |
| 请求体 | JSON 中 question 与 role | 不是可以任意执行的 Python 代码 |

HTTP 是客户端与服务端交换请求/响应的协议。GET 读取资源，POST 发送结构化请求。状态 200 表示正常响应；422 表示请求不符合字段约束；409 在本课程表示数据或索引版本冲突；503 表示必要上游产物缺失。

ASGI 是 Python Web 服务与服务器之间的接口。FastAPI 定义请求规则和处理函数，Uvicorn 负责监听端口并把网络请求送入应用。请结合本实验的启动命令和接口调用，观察 FastAPI 与 Uvicorn 如何协作。

## 5. 阶段二：真正调用问答接口

```powershell
$body = @{question="模拟服务的用户每周CPU推理配额是多少分钟？"; role="public"} | ConvertTo-Json
$bytes = [System.Text.Encoding]::UTF8.GetBytes($body)
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/ask -ContentType "application/json; charset=utf-8" -Body $bytes | ConvertTo-Json -Depth 10
```

`ConvertTo-Json` 把 PowerShell 字典变成请求文本；`UTF8.GetBytes` 明确中文编码；`-Method Post` 表示向问答路由提交请求。响应应包含 `answer`、`citations`、`hits`、`data_version`、`index_version`、`cache_hit`。

首次启动后同一问题第一次通常 `cache_hit=false`，再次执行应为 true。如果该问题之前已被本人执行的其他命令调用，第一次可见结果也可能命中；请记录服务进程的启动状态和先前请求，按实际缓存状态解释结果。

请求模型的关键约束：

```python
class AskRequest(BaseModel):
    question: str = Field(min_length=1, max_length=1000)
    role: Literal["public", "internal"] = "public"
```

Pydantic 根据类型与长度约束检查请求。字符串存在不等于非空白问题合法，后续检索函数仍会检查。生产服务还需要更完整的输入边界与身份验证，本实验先掌握结构约束和错误可见性。

### 5.1 权限对照

分别把问题改为“内部维护窗口是什么时间？”，role 设为 public 和 internal，运行两次。public 应拒答，internal 可以检索虚构维护规则。观察每个响应自己的 role 与引用，不能仅比较屏幕上的一句自然语言答案。

## 7. 阶段四：缓存身份与版本校验

`cache_key()` 对以下字段组成的数组计算 SHA256：规范化问题、role、文档版本、索引版本、生成器、统计版本。规范化仅压缩空白，避免改动问题真实语义。

```python
identity = [" ".join(question.split()), role, data_version,
            index_version, generator, stats_version]
```

哈希用于压缩和稳定标识，不会自动使缓存“安全”。真正重要的是输入身份包含必要字段，尤其是权限与版本。

```powershell
.\.venv\Scripts\python.exe -m coursekit capture --lab 07 --stage probe-02 -- .\.venv\Scripts\python.exe -c "from coursekit.service import cache_key; print(cache_key('配额','public','d1','i1')); print(cache_key('配额','internal','d1','i1')); print(cache_key('配额','public','d2','i1'))"
```

三行应不同。相同问题但角色不同或数据变化，必须重新取得合法结果。对于统计工具，缓存还包含增量汇总的 SHA256。

`ask_payload()` 每次先 `load_index()` 检查源文件和索引哈希，再查询缓存。如果先返回缓存后才发现源数据变化，旧答案就已经泄露到响应中了。

本课缓存位于单个 Python 进程内，最多 256 项，满时删除最早插入项；它不是分布式 Redis，也不是 LRU。重启会丢失缓存，多个服务进程不共享缓存。锁保护字典修改，但并发同一冷请求仍可能重复计算；这不属于本课已解决的能力。

## 8. 阶段五：20 次真实请求与指标

保持终端 A 运行，在终端 B 执行：

```powershell
.\.venv\Scripts\python.exe -m coursekit lab07 --requests 20
Invoke-RestMethod http://127.0.0.1:8000/metrics | ConvertTo-Json -Depth 8
```

测试客户端通过真实 HTTP 顺序发送请求，每五次中一次调用统计工具，其余问配额。默认只有两种不同问题，因此热缓存命中率较高。新进程上直接运行测试时通常 18 次命中；如果之前已经预热可能更多。错误应为 0，逐条状态应为 200。

| 字段 | 单位或分母 | 解读 |
|---|---|---|
| p50_ms | 毫秒 | 一半测得请求不高于该值 |
| p95_ms | 毫秒 | 95% 位置的样本分位数，20 条样本还很不稳定 |
| throughput_requests_per_second | 本次请求数/墙钟秒数 | 串行调用下的实测速率，不是最大承载量 |
| error_rate | 失败请求数/本次请求数 | 包括4xx/5xx，不能只报告成功样本 |
| cache_hit_rate | 命中次数/本次请求数 | 与问题重复程度和预热状态强相关 |
| server_metrics_before/after | 当前单进程累计 | 包括健康和指标请求，不能直接当本次20题分母 |

服务端的计时在 middleware 中完成，客户端计时还包含本机网络、序列化与等待。因此两者不会完全相同。`/metrics` 最多保留最近 10000 条延迟样本，进程重启清零，不能把它当长期监控数据库。

## 11. 容器部署迁移对照

Docker 镜像是打包应用与依赖的只读模板；容器是模板启动出的进程；挂载把外部目录交给进程使用；端口映射把宿主机地址转发到容器。容器有自己的文件路径，不能直接使用 Windows 的 `C:\...` 绝对路径。

请先阅读根目录中的 Dockerfile 与 compose.yaml：

```powershell
Get-Content .\Dockerfile
Get-Content .\compose.yaml
```

Dockerfile 复制应用源码并安装 Linux 容器依赖，入口同样是 Uvicorn。compose 将 `./data` 只读挂载为 `/workspace/data`，把输出写到宿主机的 `outputs/container`；`BDP_ROOT=/workspace` 告诉 common.py 去哪里找数据。

容器内 Uvicorn 绑定 0.0.0.0 是为了接收容器网络转发；宿主机映射仍是 `127.0.0.1:8000:8000`，只供本机访问。这两个地址所在的网络环境不同，不能只看到 0.0.0.0 就改成公网开放。

先在终端 A 用 Ctrl+C 停止原生 Uvicorn，再执行：

```powershell
docker compose build
if ($LASTEXITCODE -ne 0) { throw '容器镜像构建失败，请检查上方错误' }
docker compose up -d --wait --wait-timeout 90
if ($LASTEXITCODE -ne 0) { throw '容器未在90秒内通过健康检查，请查看 docker compose logs' }
docker compose ps
Invoke-RestMethod http://127.0.0.1:8000/health | ConvertTo-Json -Depth 8
```

`--wait` 会等到 compose 中的健康检查通过才返回，`--wait-timeout 90` 给出90秒等待上限；仅用 `up -d` 时容器可能仍在加载依赖，立即发请求会连接失败。应能看到容器运行和健康状态。首次 build 可能下载镜像与依赖；使用本地缓存时，先核对镜像与依赖版本。数据应保持词法索引，因为该轻量容器不包含大模型依赖。真实模型与 HTTP 服务分开部署时，需要分别配置依赖、调用地址和失败处理。

```powershell
.\.venv\Scripts\python.exe -m coursekit lab07 --requests 20
docker compose logs --tail 30
docker compose stop
```

同一个测试客户端不必更改 URL，这是部署封装的价值。`stop` 停止本课程容器，不删除数据。不要执行会清除卷或未知容器的全局清理命令。再次启动可用 `docker compose up -d`。

原生路径按第 12 节的完整清单验收，Docker 对照作为可选拓展。请说明端口和数据路径；运行容器前，先停止占用宿主机 8000 端口的原生服务。

## 12. 常见问题与结果检查

| 现象 | 处理 |
|---|---|
| 端口8000已占用 | 查看是否上一终端还在运行；先正常停止自己的旧服务，不终止未知进程 |
| 连接被拒绝 | 确认终端 A 仍运行，URL端口一致，服务没有启动失败 |
| 409 | 读取响应中的版本冲突原因，先修复数据/索引关系 |
| 503缺少统计 | 完成实验04，检查BDP_ROOT与路径 |
| 中文请求乱码 | 使用UTF8字节与charset；核对输入JSON |
| 改源码后行为不变 | 本课程未启用自动重载；停止并重新启动服务 |
| p95比别人高 | 检查缓存、后台负载、客户端顺序、容器限制，不修改实测值 |
| cache_hit全为True | 可能已经预热；记录进程是否新启动，并按实际状态标明冷启动或热缓存 |
| Docker启动失败 | 确认 Docker Desktop 已启动且本机 Linux 容器后端可用；执行 `docker compose ps` 查看状态，构建失败时检查原 `build` 输出，执行 `docker compose logs --tail 30` 查看容器启动后的服务日志，并检查 8000 端口占用与目录挂载 |
| 容器读不到文件 | 检查挂载、BDP_ROOT和先前是否生成索引；不在容器里重seed覆盖数据 |

最终验收应包含带学号的 20 请求结果、统计一致性、角色/缓存对照、一项关键代码差异和一项故障记录。实验 08 会检查 `load_test.json` 的请求数、错误数和索引版本。
